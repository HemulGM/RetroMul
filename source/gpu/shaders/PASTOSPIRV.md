# Pascal compute sources

All PSP LLE and HLE `.pasm` sources are embedded as RCDATA by `PSPGE.Pascal.rc`.
The backends compile that text directly to SPIR-V
at context startup through `PTS.Component.TShaderCompilerComponent`, linked from
the `dependencies/PasToSPIRV` submodule. The driver then builds its usual Vulkan
pipeline. No external compiler, source filesystem lookup or Vulkan SDK is used
at runtime.

The external entry point remains `main`. LLE bindings 0..7 and its push-constant
layout are unchanged. Each immutable embedded module is compiled once per
process and its SPIR-V is reused when another context is created. Compilation
errors include the logical source name, line and column; the backend reports
initialization failure rather than silently loading a stale SPV array.

Initialize submodules before building. The Delphi project's `RcCompile` item
builds the resource; the fork-only headless build scripts do the same with cgrc.
The generated `.res` is a build artifact, not a committed source file.

PasToSPIRV 1.4.0 supports the runtime component, explicit graphics stages and
Vulkan11 profile. No legacy PSP GLSL sources or generated PSP SPIR-V units
remain in the production tree.
Frozen instruction streams for compiler comparisons are maintained only in the
development fork's tests, not linked by the frontend or regenerated by the
production shader script.

HLE uses native Vertex/Fragment stages for its graphics pipelines, including
NoPerspective/Flat interfaces, fragment depth, fine derivatives, Discard and
ordered pixel interlock. Down-sampling/stencil mirroring and CLUT lookup remain
compute stages. The 88/32/40-byte push layouts, descriptor sets, formats and
integer colour operations are unchanged. Shared push/shade/blend text is resolved
from explicit embedded virtual includes, without source filesystem access.

GLSL development shaders and their offline compiler script are maintained only
in the development fork's GPU tests. Ordinary PSP builds and execution need
neither those utilities nor glslc.

`SoftDouble.pasm` is a vendored module from PasToSPIRV under the MIT license in
`dependencies/PasToSPIRV/LICENSE`. The former adjacent license file duplicated
that notice; attribution and license terms remain in the dependency.

## Numerical and layout details

- `[Vulkan11, StrictFloat]` emits the required 32/64-bit float controls and
  NoContraction decorations directly (no assembly patch after compilation).
- Native Byte/Word buffers preserve 8/16-bit reads and 16-bit stores. Aliased
  VRAM views are explicitly marked `[Aliased]`; no 32-bit read-modify-write is
  substituted for a 16-bit write.
- Integer GLSL `/` becomes `div`. Signed GLSL `>>` becomes
  `ArithmeticShiftRight` where sign extension is required; Pascal `shr` is
  logical, matching the CPU reference's logical shifts.
- Double division uses SoftDiv. Divisions by 16 become multiplication by the
  exact reciprocal. Fog division by 255 uses SoftDiv followed by Single
  rounding, retaining the CPU fog index rather than depending on native GPU
  division accuracy.
- Texture-reader temporary state is an explicit invocation-local record passed
  by reference, not mutable module globals. Fragment records are initialized
  before passing to routines with early rejection paths.
- Resources remain packed word arrays; host record layout is not inferred from
  the compiler's records.

## Vulkan 1.1 and 1.2

The compute context prefers the existing Vulkan 1.2 device path and uses its core
feature chain unchanged. A Vulkan 1.1 device enables the supported equivalent
KHR extensions for 8-bit storage, int8, float controls and timeline semaphores.
Timeline entry points also resolve their KHR aliases. Unsupported feature
structures are not queried or passed to device creation.

The native HLE modules target SPIR-V 1.3 / Vulkan 1.1 and are valid on both
1.1 and 1.2 devices. This does not cap a capable device to API 1.1: device
negotiation still prefers 1.2 and its core feature path. There are no separate
precompiled `V11` arrays or shader-version branches in the draw loop. Interlock
remains optional and its existing fixed-function fallback is preserved.

API compatibility does not emulate absent shader arithmetic. LLE still requires
native int64/float64, small storage and the IEEE float controls, and retains its
GPU arithmetic qualification. For example, Mali-G57 can use HLE through Vulkan
1.1 but does not qualify for native LLE because it lacks int64/float64. Missing
features are reported; neither precision nor required fallbacks are weakened.

The differential regression suite is maintained separately in the development
fork; it is not a dependency of the shader integration or application builds.
